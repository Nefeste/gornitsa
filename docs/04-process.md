# Как ведётся работа

Порядок работы одинаков во всех проектах студии. Здесь — общее; в `docs/05-process.md`
проекта — только его особенности: где лежит номер версии, какие workflow, как выкладывается
его сервер, чек-лист выпуска с его шагами.

## Документация живёт в репозитории

Всё, что нужно, чтобы вести проект, ничего не помня о нём заранее, лежит в репозитории
проекта, в `docs/`, на русском. Переписка и память агента — не место для договорённостей.

Устройство документов одинаковое (так легче переходить между проектами):

| Файл | Что в нём |
|---|---|
| `README.md` (корень) | что за проект, как запустить; раздел на каждую версию — что изменилось для игрока |
| `AGENTS.md`, `CLAUDE.md` | вход для ИИ-агентов: ссылка на устав, порядок чтения, команды, правила проекта |
| `docs/README.md` | оглавление и порядок чтения документов проекта |
| `docs/01-product.md` | что за игра, для кого, что обещаем, чего сознательно нет, словарь |
| `docs/02-architecture.md`, `03-server-api.md`, `04-data-model.md` | как устроено |
| `docs/05-process.md`, `06-testing.md` | особенности процесса и проверок проекта |
| `docs/07-roadmap.md` | этапы, задачи владельца, открытые вопросы, журнал |
| `docs/08…` | предметные документы игры: правила, мир, геймдизайн, контент, деньги, рынок |
| `docs/adr/` | решения проекта, которые дорого менять |
| `docs/specs/` | спецификации возможностей, пишутся до кода |
| `store/` | материалы для RuStore и страницы игры на сайте |

**Рабочее правило:** изменение кода, из-за которого документ стал неверным, не закончено.
Документ правится в том же коммите.

## Правила документов

- **Русский язык, человеческие формулировки.** Документы читают люди, пишут их чаще агенты;
  и тем и другим проще, когда написано просто. `AGENTS.md` — по-английски.
- **Одно место для факта.** Общее для студии — только в уставе; в проекте — одно место для
  каждого своего факта (правила игры, числа геймдизайна, протокол, рыночные цифры, право
  и деньги), в остальных местах — ссылка. Копия неизбежно разойдётся с оригиналом.
- **Документ описывает то, что есть.** Задуманное, но не сделанное, живёт в `specs/`
  и в дорожной карте и помечено. Пока кода нет, документы описывают принятый проект.
- **Гипотезы отделены от фактов.** Цены, частоты, цели удержания, стартовые числа — гипотезы
  и помечены так. Факты — со ссылкой на источник и датой; собранное по поисковой выдаче —
  с пометкой «сверить».
- **Утверждение, на котором держится механика, — с источником**: правило — со сводом,
  сказка — с изданием, медицина — с клинической рекомендацией ([`06-content.md`](06-content.md)).
- **Комментарии в коде — про «почему».** Документация — про устройство и договорённости,
  код — про «как». Не пересказывайте код в документации.

## Жизненный цикл возможности

«Сначала спецификация, потом код» (SDD — specification-driven development):

1. Проверка по обещаниям ([`02-values.md`](02-values.md#как-проверить-новую-возможность)).
2. Спецификация `docs/specs/<год>-<месяц>-<название>.md`: что должно получиться, экраны,
   данные, запросы, неудачные случаи, критерии приёмки.
3. Код и тесты по спецификации.
4. Правка затронутых документов и дорожной карты; ADR, если решение дорого менять.
5. Выпуск по чек-листу ([ниже](#выпуск) и в `05-process.md` проекта).

Мелкие правки (текст, цвет, исправление ошибки) спецификации не требуют — только запись
в разделе версии корневого `README.md`.

**Потоки записей.** Контент (сказы, болезни, картинки, карточки) и баланс идут не
спецификациями, а записями и отчётами: запись в `content/` по правилам проекта, валидатор,
отчёт «виртуального игрока» или «виртуального врача» в описании коммита.

## ADR

Короткая записка о решении, которое дорого менять. Отвечает на вопросы: **что решили,
почему, чем платим** и, если есть, **когда пересмотреть**. Файл `NNNN-краткое-название.md`
в `docs/adr/` проекта или в [`adr/`](../adr/README.md) устава.

- ADR не переписывается задним числом. Передумали — новая записка «заменяет NNNN»,
  у старой в заголовке «(заменено NNNN)».
- Решение, общее для всех игр, — ADR студии, а не проекта. ADR проекта может применять
  ADR студии («как это сделано у нас») или отступать от него с разрешения владельца.
- Читать ADR **до** того, как предлагать обратное.

## Версии

- **Третье число** — исправления и мелочи; **второе** — заметная возможность;
  **первое** — смена обещания игроку, а не объём нового.
- Первый выход в магазин — `1.0.0` (у «Вотчины» исторически `2.0.0`). С него сервер обязан
  понимать предыдущую выпущенную версию приложения (ADR студии [0005](../adr/0005-offline-first-own-server.md)).
- `versionCode` — +1 на каждую сборку, ушедшую в магазин; второй файл с тем же номером
  магазин не примет, даже если первый не вышел.
- Номер версии живёт в нескольких файлах (`app.json`, `package.json`, `package-lock.json`,
  «Об игре»); тест проекта сверяет их. Где именно — `05-process.md` проекта.
- Каждой версии — раздел в корневом `README.md`: что изменилось для игрока, человеческим
  языком. Тот же текст, короче, идёт в «Что нового» RuStore и в «Об игре».

## Ветки и CI

- `main` — всегда то, что можно выпустить. Работа — в ветках (`claude/<задача>` у агентов),
  в `main` — через PR. Сливает владелец.
- **CI собирает только после слияния в `main`** и по ручному запуску (решение владельца
  от 27.09.2026): минуты GitHub Actions общие на все закрытые репозитории владельца
  (бесплатно — 2000 минут в месяц), а сборка APK — 15–30 минут. На рабочих ветках и PR
  сборка не запускается.
- Поэтому **перед каждым push** агент сам прогоняет то, что прогнал бы CI: типы, линтер,
  тесты, для изменений интерфейса — веб-сборку и сценарий в браузере. Команды — в `AGENTS.md`
  проекта.
- Изменения, которые не должны запускать сборку (только документы), либо попадают под
  `paths-ignore`, либо помечаются `[skip ci]` в заголовке коммита.
- Долгие работы (обучение нейросетей, большие прогоны) в CI не идут: они делаются локально,
  а результат попадает в репозиторий файлом с паспортом.

**Расхождения на 27.09.2026** (привести к правилу или записать отступление): `android.yml`
«Длинных нард» запускает проверки на push в `claude/**`; `android.yml` «Анамнеза» — на
`pull_request`.

## Как загружается код

Если у агента есть `git push` (облачная сессия с доступом к репозиторию) — обычные коммиты
в рабочую ветку и PR.

Если прямого доступа нет — через веб-интерфейс GitHub в браузере. Порядок, который себя
оправдал:

1. Собрать набор изменённых файлов вместе с их `sha-256`.
2. Готовить файлы в самом браузере: брать текущий файл из репозитория по коммиту и применять
   к нему правку, а не переносить файлы целиком через чат.
3. Прикладывать файлы к форме загрузки **с полными путями** в имени, иначе GitHub положит их
   в корень репозитория.
4. Один коммит — одно осмысленное изменение; для PR — новая ветка из формы коммита.
5. После коммита перечитать каждый файл с сервера и сверить `sha-256` с ожидаемым.

Большие служебные файлы (`package-lock.json`) не переносятся целиком: они собираются
в браузере из лежащего в репозитории — переносятся только добавленные и изменённые записи,
а готовый файл сверяется по `sha-256`.

## Общий код игр

Каждая игра — свой репозиторий; общее переносится **копированием** с пометкой источника
в первой строке файла (ADR студии [0002](../adr/0002-copy-not-share.md)):

```ts
// из votchina: src/ui/dialog.tsx @ 9f587e7
```

Исправление в скопированном коде — задача перенести его в остальные копии; список копий
находится поиском по строке `// из <репозиторий>: <путь>`.

## Выпуск

Общая часть чек-листа; шаги проекта — в его `05-process.md`.

1. Все проверки проекта зелёные локально; «виртуальный игрок» — если менялся баланс.
2. Номер версии поднят во всех местах, раздел версии в `README.md` написан.
3. Материалы `store/` соответствуют версии: описание, «Что нового», снимки, анкеты `forms.md`.
4. Если изменилось, что игра собирает или отправляет, — раздел игры в политике
   конфиденциальности на сайте поправлен до выпуска ([`07-privacy.md`](07-privacy.md)).
5. Сборка подписана постоянным ключом (ADR студии [0006](../adr/0006-permanent-app-id-and-key.md));
   проверка подписи — в CI.
6. Сервер понимает предыдущую выпущенную версию приложения (если сервер есть).
7. Владелец проверил сборку на телефоне и сам публикует версию в RuStore
   ([`08-publishing.md`](08-publishing.md)).

## Если контекст потерян

Агент, начинающий с нуля, должен:

1. Прочитать `AGENTS.md` устава и этот документ, потом `AGENTS.md` и `docs/README.md` проекта.
2. Посмотреть историю коммитов и раздел версий в `README.md` проекта — это даёт состояние.
3. Открыть `docs/07-roadmap.md` проекта — там написано, что делается сейчас и какие вопросы
   ждут владельца.
4. Открыть спецификацию текущего этапа в `docs/specs/`.

## Новый проект

1. Проверка замысла по миссии и обещаниям ([`01-mission.md`](01-mission.md), [`02-values.md`](02-values.md)).
2. Репозиторий `Nefeste/<имя латиницей>`; идентификатор приложения `games.gornitsa.<имя>` —
   выбирается один раз (ADR студии [0006](../adr/0006-permanent-app-id-and-key.md)).
3. Документы по устройству выше; `docs/adr/0001` проекта — какие ADR студии применяются
   и как, без пересказа.
4. `AGENTS.md` начинается с блока ниже; `CLAUDE.md` — одна строка `@AGENTS.md`.
5. Вид игры — по брендбуку ([`../brand/README.md`](../brand/README.md#как-игры-носят-бренд-студии)).
6. Страница игры на сайте и раздел в политике конфиденциальности — к первому закрытому тесту.

Блок для начала `AGENTS.md` проекта:

```markdown
## Studio charter — read first

This project belongs to the «Горница» studio. Studio-wide rules live only in the public
charter repository `Nefeste/gornitsa` (https://github.com/Nefeste/gornitsa); this repository
keeps only what is specific to the project. Before changing anything — and after a context
reset — read the charter's `AGENTS.md`, then `docs/05-rules.md` (hard rules for every game)
and `docs/04-process.md` (how work is done). Raw files:
`https://raw.githubusercontent.com/Nefeste/gornitsa/main/<path>`.

Precedence: the owner's recorded decision → the charter → this project's documents. A project
rule may narrow a charter rule, never weaken it. If a document here restates or contradicts
the charter, replace it with a link or report the contradiction to the owner.
```
